\# 2. Project Identity



\## Project Name



VASTRIX



\## Product Type



Secure large-file transfer and file-sharing platform.



\## Original Project Name



FileFlow



The project was originally referred to as FileFlow. The current backend/API namespace and product identity are VASTRIX.



\## Primary Goal



VASTRIX is intended to allow users to:



1\. Create an account.

2\. Upload one or multiple large files.

3\. Create a secure transfer.

4\. Configure transfer expiration and security options.

5\. Generate a secure sharing link.

6\. Share the link with a recipient.

7\. Allow the recipient to verify their identity where required.

8\. Allow secure file downloads.

9\. Automatically clean up expired transfers and files.



The platform is intended to be self-service and require minimal manual administration.

\# 25. TUS Authorization Flow



The backend currently validates:



1\. JWT authentication

2\. Authenticated principal

3\. User NameIdentifier

5\. Maximum upload size

The backend therefore remains the final authority for upload limits.

\# 26. TUS File Completion



After upload completion, the backend:



1\. Revalidates authentication.

2\. Reads upload metadata.

3\. Validates transfer ownership.

4\. Validates transfer expiration.

5\. Determines physical storage path.

6\. Checks physical file existence.

7\. Checks actual file size.

8\. Starts database transaction.

9\. Locks user row.

10\. Revalidates user state.

11\. Recalculates storage usage.

12\. Rechecks quota.

13\. Creates TransferFile metadata.

14\. Saves changes.

15\. Commits transaction.



If an error occurs, the database transaction is rolled back.



Potential remaining concern:



If database persistence fails after a physical file has already been created, an orphan physical file can remain.

\# 42. Security Principles



VASTRIX should follow these principles:



1\. Files must never be publicly exposed by permanent public URLs.

2\. Large files must not be stored in PostgreSQL.

3\. Database stores metadata.

4\. Ownership must be determined from authenticated identity, not client-supplied owner IDs.

5\. User data must be isolated.

6\. Transfer tokens must be treated as secrets.

7\. Download access must validate transfer state and expiration.

8\. File paths must remain inside the configured storage root.

9\. Sensitive authentication data must not be logged.

10\. Security controls must be enforced server-side.

11\. Frontend validation is UX, not security.

12\. Do not weaken backend authorization to solve frontend integration problems.

\## Rule 3 — Inspect Actual Source



Documentation is not a substitute for source-code verification.



\## Rule 4 — Do Not Assume



If implementation is unclear, inspect the source.



\## Rule 5 — Preserve Existing Architecture



Do not rewrite working systems unnecessarily.



\## Rule 6 — Do Not Introduce Infrastructure Without Need



Do not add Redis, Docker, Kubernetes, queues, object storage, or other infrastructure merely because they are common technologies.



\## Rule 7 — Security First



Never expose:



\* Passwords

\* Password hashes

\* JWT secrets

\* JWT tokens

\* OTP codes

\* SMTP passwords

\* Connection strings

\* API keys

\* Other secrets



\## Rule 8 — Server-Side Security Is Authoritative



Never rely on frontend validation for security.



\## Rule 9 — Test Changes



After meaningful changes:



\* Build

\* Run relevant tests

\* Verify API behavior

\* Verify frontend behavior

\* Check logs

\* Check database impact where relevant



\## Rule 10 — Update Documentation



After significant implementation changes, update the relevant project memory and technical documentation.



\## Rule 11 — Record Important Decisions



Architecture decisions should be recorded so future AI tools and developers understand why the system was built that way.



\## Rule 12 — Track Implementation State



Use these states:



```text

IMPLEMENTED

PARTIALLY IMPLEMENTED

PLANNED

MISSING

BLOCKED

DEPRECATED

```



Do not mix these states.
