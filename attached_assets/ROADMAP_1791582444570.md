\# VASTRIX — Product Roadmap



\## 1. Document Purpose



This document defines the planned development path for VASTRIX.



It provides a high-level view of:



\* What has already been built

\* What is currently being completed

\* What should be completed next

\* What is planned for the MVP

\* What is planned after the MVP

\* What should not be implemented prematurely



This roadmap is intentionally separate from detailed technical documentation.



Actual implementation status must always be verified against source code and the current project memory.



\---



\# 2. Roadmap Status Legend



Use the following status values:



| Status       | Meaning                                                 |

| ------------ | ------------------------------------------------------- |

| COMPLETED    | Implemented and verified                                |

| PARTIAL      | Some functionality exists but the feature is incomplete |

| NEXT         | Intended immediate development                          |

| PLANNED      | Intended future work                                    |

| BLOCKED      | Cannot proceed until another dependency is resolved     |

| DEFERRED     | Intentionally postponed                                 |

| NOT REQUIRED | Outside the current product scope                       |

\# 25. Current Technical Blockers



Important current blockers/dependencies:



\## Frontend Authentication



The backend requires JWT authentication for protected transfer creation and TUS upload, but the current frontend flow does not send the JWT.



This blocks the complete authenticated sender workflow.



\## API Port Configuration



The frontend currently contains inconsistent API URLs.



The backend normally runs on port 8080 while transfer creation currently contains a hardcoded port 5000.



This must be corrected.



\## Recipient Verification



The database foundation exists, but the complete recipient verification workflow is not implemented.



This blocks treating recipient verification as a complete security feature.

\# 27. Development Strategy for the Current Machine



The development environment has limited hardware resources.



Therefore:



\* Prefer simple local development.

\* Avoid unnecessary infrastructure.

\* Avoid running multiple heavy services simultaneously.

\* Keep local storage architecture simple during development.

\* Add infrastructure only when required.

\* Prefer incremental implementation.

\* Test each module before moving to the next.

\# 29. Roadmap Governance



The roadmap is not a promise that every future feature will be implemented.



It is a planning document.



Requirements may change.



When requirements change:



1\. Update the roadmap.

2\. Record the decision if significant.

3\. Update product requirements.

4\. Update affected architecture documentation.

5\. Update implementation status.

6\. Do not leave obsolete plans appearing as active requirements.



\---



\# 30. Roadmap Principle



The roadmap should always answer three questions:



\### Where are we?



Current implementation status.



\### What are we doing next?



Immediate development priorities.



\### Where are we going?



Longer-term product and technical direction.



The roadmap must remain synchronized with the real VASTRIX project.
