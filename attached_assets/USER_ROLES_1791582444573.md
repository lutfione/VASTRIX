\# VASTRIX — User Roles \& Permissions



\*\*Document Type:\*\* Project Memory

\*\*Product:\*\* VASTRIX

\*\*Purpose:\*\* Define product-level roles, responsibilities, security boundaries, and current implementation status.

\*\*Status:\*\* Baseline memory document

\*\*Last Updated:\*\* 2026-09-16



\---



\## 1. Purpose



VASTRIX has several conceptual user types based on how a person interacts with the platform.



The product-level roles are:



1\. Guest

2\. User

3\. Recipient

4\. Admin



These roles describe the intended product behavior.



\*\*Important:\*\* The current backend does not implement all four as application/database roles.



The current backend `UserRole` enum contains only:



```text

User = 0

Admin = 1

```



Therefore:



\* `User` and `Admin` are actual authenticated backend roles.

\* `Guest` is currently a product-level/anonymous access state.

\* `Recipient` is currently a product-level/transfer-recipient state.

\* Guest and Recipient must not be treated as implemented database roles.

\# 2. Role Model



```text

&#x20;                   VASTRIX

&#x20;                      │

&#x20;       ┌──────────────┼──────────────┐

&#x20;       │              │              │

&#x20;     Guest           User           Admin

&#x20;       │              │              │

&#x20;Anonymous         Authenticated   Authenticated

&#x20;access            account         administrator

&#x20;       │

&#x20;       └────── Recipient ────────┐

&#x20;                                 │

&#x20;                        Recipient is a

&#x20;                        transfer-specific

&#x20;                        access context

```



A person may interact with VASTRIX differently depending on the action being performed.



For example:



\* A person visiting the marketing site is a Guest.

\* A registered account owner creating a transfer is a User.

\* A person opening a shared transfer link is a Recipient context.

\* An administrator managing the system is an Admin.



\---



\# 3. Guest



\## 3.1 Definition



A Guest is an unauthenticated visitor who has not established an authenticated VASTRIX user session.



Guest access is primarily intended for:



\* Visiting the public website.

\* Viewing public product information.

\* Accessing a transfer link when the transfer allows anonymous access.

\* Entering recipient verification information when required.

\* Downloading files when all required transfer security conditions are satisfied.



Guest does not represent a database `UserRole`.



\---



\## 3.2 Intended Permissions



| Capability                       | Guest               |

| -------------------------------- | ------------------- |

| View landing page                | Yes                 |

| View public product pages        | Yes                 |

| Register                         | Yes                 |

| Login                            | Yes                 |

| Create authenticated transfer    | No                  |

| View own authenticated dashboard | No                  |

| Access transfer by secure token  | Yes, when permitted |

| View transfer details            | Yes, when permitted |

| Download transfer files          | Yes, when permitted |

| Access admin functions           | No                  |

| Manage another user's transfers  | No                  |



\---



\## 3.3 Security Boundary



Guest access must never provide authenticated-user privileges.



A Guest must not be able to:



\* Choose another user's ID.

\* Access another user's dashboard.

\* Modify another user's transfer.

\* Access administrative endpoints.

\* Bypass transfer expiration.

\* Bypass recipient verification.

\* Bypass transfer password protection.

\* Bypass download restrictions.



The secure transfer token is treated as a secret capability and must not be considered equivalent to an authenticated account.



\---



\# 4. User



\## 4.1 Definition



A User is a registered and authenticated VASTRIX account holder.



The User is the primary sender/owner of transfers.



The current backend represents this role using:



```csharp

UserRole.User

```



\---



\## 4.2 Intended Responsibilities



A User should be able to:



\* Register an account.

\* Authenticate.

\* Create transfers.

\* Upload files.

\* Manage their own transfers.

\* Generate secure transfer links.

\* Configure transfer expiration.

\* Configure recipient verification.

\* Configure password protection.

\* Monitor transfer state.

\* Access download-related information.

\* Manage available account/storage quota.



\---



\## 4.3 Current Backend Permissions



The current backend supports authenticated User access to:



```text

GET  /api/Transfer

POST /api/Transfer/create

/api/upload-stream

```



Transfer ownership is derived from the authenticated JWT identity rather than from a client-supplied owner ID.



The backend currently restricts the transfer listing to the authenticated user's own non-deleted transfers.



\---



\## 4.4 Security Boundary



A User must only be able to operate on resources they own or are explicitly authorized to access.



The backend must not trust:



\* Client-supplied user IDs.

\* Client-side ownership claims.

\* Frontend-only authorization.

\* Hidden form fields as security controls.

\* JavaScript state as proof of authorization.



Authorization must be enforced server-side.



\---



\# 5. Recipient



\## 5.1 Definition



A Recipient is the person who receives access to a transfer created by a User.



Recipient is currently a \*\*conceptual product role\*\*, not a backend `UserRole`.



A Recipient should ideally not need to create a full VASTRIX account for normal file downloading.



\---



\## 5.2 Intended Recipient Flow



The intended secure recipient flow is:



```text

User creates transfer

&#x20;       ↓

Secure transfer link

&#x20;       ↓

Recipient opens link

&#x20;       ↓

Transfer security requirements evaluated

&#x20;       ↓

Recipient verification if enabled

&#x20;       ↓

Optional password verification

&#x20;       ↓

Authorized download access

```



\---



\## 5.3 Intended Recipient Permissions



| Capability                          | Recipient         |

| ----------------------------------- | ----------------- |

| Open transfer link                  | Yes               |

| View permitted transfer information | Yes               |

| Complete email verification         | Yes, when enabled |

| Enter transfer password             | Yes, when enabled |

| Download permitted files            | Yes               |

| Create/manage sender transfers      | No                |

| Access sender dashboard             | No                |

| Access admin functions              | No                |

| Access unrelated transfers          | No                |



\---



\## 5.4 Recipient Security Boundary



Recipient access must be limited to the specific transfer being accessed.



A Recipient must not gain access to:



\* The sender's account.

\* Other transfers belonging to the sender.

\* Other users' transfers.

\* Administrative endpoints.

\* Internal storage paths.

\* Database information.

\* Permanent public storage URLs.



Recipient authorization should be transfer-specific.



\---



\# 6. Recipient Verification



Recipient verification is intended to provide an additional security layer for shared transfers.



The planned mechanism is email-based one-time verification.



Conceptually:



```text

Recipient opens transfer

&#x20;       ↓

Enter recipient email

&#x20;       ↓

Server generates verification code

&#x20;       ↓

Code sent by email

&#x20;       ↓

Recipient enters code

&#x20;       ↓

Server validates code

&#x20;       ↓

Recipient receives authorized access

```



The database already contains the foundation for this mechanism through:



```text

RecipientVerificationChallenge

```



The entity contains:



\* TransferId

\* RecipientEmail

\* CodeHash

\* CodeExpiresAt

\* AttemptCount

\* CreatedAt

\* ConsumedAt



However, the complete verification flow is not currently implemented or enforced.

\# 7. Admin



\## 7.1 Definition



Admin is an authenticated administrative account.



The current backend represents this role using:



```csharp

UserRole.Admin

```



Admin privileges must be explicitly authorized by the backend.



\---



\## 7.2 Intended Responsibilities



An Admin is intended to manage and monitor platform-level operations such as:



\* System health.

\* User administration.

\* Transfer administration.

\* Storage monitoring.

\* Security monitoring.

\* Operational diagnostics.

\* Audit information.

\* Platform configuration where applicable.



Admin access should be minimized according to least-privilege principles.



\---



\## 7.3 Current Admin Capability



The current backend exposes:



```text

GET /api/admin/health

```



This endpoint requires the Admin role.



The current implementation does not yet represent a complete administration module.



\---



\# 8. Backend Role Implementation



Current backend enum:



```csharp

public enum UserRole

{

&#x20;   User = 0,

&#x20;   Admin = 1

}

```



Therefore:



| Product Concept | Current Backend Representation              |

| --------------- | ------------------------------------------- |

| Guest           | Anonymous request / unauthenticated context |

| User            | `UserRole.User`                             |

| Recipient       | Transfer-specific anonymous access context  |

| Admin           | `UserRole.Admin`                            |



This distinction is important for future development.



Do not modify the backend enum simply to make the conceptual product model match the four-role documentation unless that change is deliberately approved as part of the architecture.

\# 9. Authentication vs Transfer Access



VASTRIX has two different access concepts.



\## 9.1 Account Authentication



Used by registered Users and Admins.



```text

Username / Email

&#x20;       ↓

Password

&#x20;       ↓

JWT

&#x20;       ↓

Authenticated principal

&#x20;       ↓

Role authorization

```



Current authentication uses JWT Bearer authentication.



\---



\## 9.2 Transfer Access



Used for people accessing a shared transfer.



```text

Secure Transfer Token

&#x20;       ↓

Transfer lookup

&#x20;       ↓

Transfer security checks

&#x20;       ↓

Recipient access

```



Transfer access is intentionally separate from the sender's authenticated account.



A recipient should not need the sender's JWT.



\---



\# 10. Ownership Model



Transfers are associated with the authenticated User through:



```text

Transfer.UserId

```



`Transfer.UserId` is currently nullable.



The ownership principle is:



```text

JWT

&#x20;↓

Authenticated User ID

&#x20;↓

Transfer.UserId

&#x20;↓

Authorized transfer operation

```



The client must not be allowed to select another user's ownership identity.

\# 11. Role-Based Security Principles



VASTRIX should follow these principles:



\### 11.1 Least Privilege



Each role should receive only the permissions necessary for its purpose.



\### 11.2 Server-Side Authorization



Frontend controls are not security boundaries.



\### 11.3 Ownership Enforcement



Authenticated operations must validate resource ownership.



\### 11.4 Transfer Isolation



A transfer token should only grant access to the specific transfer associated with that token.



\### 11.5 Expiration Enforcement



Expired transfers must not remain downloadable.



\### 11.6 Verification Enforcement



If recipient verification is enabled, access must not be granted until verification succeeds.



\### 11.7 Administrative Isolation



Admin endpoints must require explicit administrative authorization.



\### 11.8 No Internal Storage Exposure



Recipients and Guests must never receive physical filesystem paths.

```text

Recipient ≠ UserRole enum value
```

The current backend only has:



```text

User

Admin
```

\# 15. Security Boundary Summary



```text

GUEST

&#x20; │

&#x20; ├── Public application access

&#x20; └── Transfer-token access when permitted

&#x20;         │

&#x20;         ▼

RECIPIENT

&#x20; │

&#x20; ├── Specific transfer only

&#x20; ├── Verification when required

&#x20; └── Download when authorized

&#x20;         

USER

&#x20; │

&#x20; ├── JWT authentication

&#x20; ├── Own transfers

&#x20; ├── Uploads

&#x20; └── Account-level resources



ADMIN

&#x20; │

&#x20; ├── JWT authentication

&#x20; ├── Admin role authorization

&#x20; └── Administrative resources

```



The fundamental security rule is:



> \*\*A person's ability to access VASTRIX must be determined by the server-side authorization context and the specific resource being accessed, not by frontend UI state.\*\*
