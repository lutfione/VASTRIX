2\. Current Entity Model



VASTRIX currently contains five primary domain entities/types:



User

&#x20;└── Transfer

&#x20;     ├── TransferFile

&#x20;     └── RecipientVerificationChallenge



UserRole

&#x20;└── enum used by User



The database-backed entities are:



User

Transfer

TransferFile

RecipientVerificationChallenge



UserRole is an enum rather than a database entity.



3\. User Entity

3.1 Business Meaning



User represents an authenticated VASTRIX account holder.



A user can:



Register an account.

Authenticate using username/email and password.

Own transfers.

Have a storage quota.

Have a role.

Be disabled by the system.



The authenticated user's database identity is also used by the backend to enforce transfer ownership.



3.2 Current C# Model

public class User

{

&#x20;   public Guid Id { get; set; } = Guid.NewGuid();

&#x20;   public string Username { get; set; } = string.Empty;

&#x20;   public string Email { get; set; } = string.Empty;

&#x20;   public string PasswordHash { get; set; } = string.Empty;

&#x20;   public UserRole Role { get; set; } = UserRole.User;

&#x20;   public bool IsDisabled { get; set; } = false;

&#x20;   public long StorageQuotaBytes { get; set; } = 5368709120;

&#x20;   public DateTime CreatedAt { get; set; } = DateTime.UtcNow;

&#x20;   public ICollection<Transfer> Transfers { get; set; } = new List<Transfer>();

}

3.3 Fields

Id

Type: Guid

Database type: uuid

Primary key.

Uniquely identifies the user.

Used by relationships from transfers.

JWT NameIdentifier contains the authenticated user's ID.

Username

Type: string

Database type: text

User's login/display username.

Required by the current entity.

Unique in the database.

Email

Type: string

Database type: text

User's email address.

Used during registration/login.

Unique in the database.

PasswordHash

Type: string

Database type: text

Stores the password hash rather than the plaintext password.

BCrypt is used by the authentication implementation.



Security rule: plaintext passwords must never be stored.



Role

Type: UserRole

Database representation: integer.

Default: User.

Used for authorization.



Current roles:



User = 0

Admin = 1

IsDisabled

Type: bool

Database type: boolean

Indicates whether the account has been disabled.

Default: false.

JWT authentication performs a database lookup and checks this state.



A valid JWT therefore does not by itself guarantee that a disabled account can continue using protected endpoints.



StorageQuotaBytes

Type: long

Database type: bigint

Represents the user's storage quota in bytes.

Current entity default:

5,368,709,120 bytes



This equals 5 GiB.



The backend uses this value during upload authorization and completion checks.



CreatedAt

Type: DateTime

Database type: timestamptz

Records account creation time.

Initialized using UTC.

Transfers

Type: ICollection<Transfer>

Navigation property.

Represents transfers owned by the user.

3.4 Relationships

User 1 ──────── \* Transfer



The relationship is:



One user can own many transfers.

A transfer may have a nullable UserId.



Therefore, the current model allows a transfer to exist without an associated user at the database/entity level.

4\. UserRole

4.1 Business Meaning



UserRole defines the authorization role assigned to a VASTRIX user.



It is an enum and is not currently a separate database table.



4.2 Current Definition

public enum UserRole

{

&#x20;   User = 0,

&#x20;   Admin = 1

}

4.3 Current Roles

User



Normal authenticated VASTRIX account.



Current protected capabilities include creating transfers and accessing the user's own transfers.



Admin



Administrative role.



An admin is currently authorized for the administrative health endpoint.



4.4 Future Considerations



The product roadmap may eventually require additional roles or permissions.



Do not add roles simply because they appear in an earlier product document.



If role requirements change:



Confirm the product requirement.

Review authorization implications.

Update the enum/database migration if necessary.

Update authorization logic.

Update project memory.

5\. Transfer Entity

5.1 Business Meaning



Transfer represents a secure file-transfer package created by a VASTRIX user.



A transfer acts as the parent container for one or more uploaded files.



Conceptually:



Transfer

&#x20;├── security/access information

&#x20;├── expiration

&#x20;├── optional message

&#x20;├── ownership

&#x20;└── files



The transfer receives a secure token that is currently used to access the recipient-facing transfer page and download files.



5.2 Current C# Model

public class Transfer

{

&#x20;   public Guid Id { get; set; } = Guid.NewGuid();

&#x20;   public Guid? UserId { get; set; }

&#x20;   public User? User { get; set; }

&#x20;   public string SecureToken { get; set; } = Guid.NewGuid().ToString("N");

&#x20;   public string? CustomMessage { get; set; }

&#x20;   public string? PasswordHash { get; set; }

&#x20;   public bool RequireRecipientVerification { get; set; } = false;

&#x20;   public DateTime CreatedAt { get; set; } = DateTime.UtcNow;

&#x20;   public DateTime ExpiresAt { get; set; }

&#x20;   public bool IsDeleted { get; set; } = false;



&#x20;   public ICollection<TransferFile> Files { get; set; } = new List<TransferFile>();



&#x20;   public ICollection<RecipientVerificationChallenge>

&#x20;       RecipientVerificationChallenges { get; set; }

&#x20;       = new List<RecipientVerificationChallenge>();

}

5.3 Fields

Id

Type: Guid

Database type: uuid

Primary key.

Internal identifier for the transfer.

UserId

Type: Guid?

Database type: uuid

Nullable foreign key to User.

Identifies the owner of the transfer when an owner exists.



The backend currently uses the authenticated user's identity when creating transfers.



User

Navigation property to User.

Represents the transfer owner.

SecureToken

Type: string

Database type: text

Unique database index.

Used as the external secure transfer identifier in recipient-facing URLs.



The current value is generated from a GUID without hyphens.



Example format:



xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx



The secure token must be treated as sensitive access material.



CustomMessage

Type: string?

Optional message associated with the transfer.

Displayed on the recipient transfer page.

PasswordHash

Type: string?

Intended to contain a hashed transfer password.

Currently exists in the entity model.



Important: the existence of this field does not mean transfer-password protection is fully implemented.



Current feature status: not implemented end-to-end.



RequireRecipientVerification

Type: bool

Default: false.

Indicates whether recipient verification is requested for the transfer.



The property exists and the transfer creation API accepts the corresponding option.



However, recipient verification is currently not fully enforced on the recipient download flow.



CreatedAt

Type: DateTime

Database type: timestamptz.

Records transfer creation time.

Uses UTC.

ExpiresAt

Type: DateTime

Database type: timestamptz.

Determines when the transfer expires.



The backend currently validates expiration when accessing transfer details and downloading files.



IsDeleted

Type: bool

Default: false.

Implements soft deletion.



A deleted transfer is excluded from normal transfer access.



Files

Navigation collection.

Contains the files belonging to the transfer.

RecipientVerificationChallenges

Navigation collection.

Contains recipient verification challenge records associated with the transfer.

6\. TransferFile Entity

6.1 Business Meaning



TransferFile represents one physical file belonging to a transfer.



A transfer can contain multiple files.



The database stores metadata, not the actual large-file contents.



The actual file is currently stored on the local filesystem.



6.2 Current C# Model

public class TransferFile

{

&#x20;   public Guid Id { get; set; } = Guid.NewGuid();



&#x20;   public Guid TransferId { get; set; }



&#x20;   public Transfer Transfer { get; set; } = null!;



&#x20;   public string OriginalFileName { get; set; } = string.Empty;



&#x20;   public long FileSizeBytes { get; set; }



&#x20;   public string ContentType { get; set; } = string.Empty;



&#x20;   public string StorageObjectKey { get; set; } = string.Empty;



&#x20;   public DateTime UploadedAt { get; set; } = DateTime.UtcNow;

}

6.3 Fields

Id

Type: Guid

Database type: uuid

Primary key.

Identifies an individual uploaded file.



The TUS upload flow also uses a file identifier during the upload process.



TransferId

Type: Guid

Database type: uuid

Required foreign key to Transfer.

Transfer

Navigation property to the parent transfer.

OriginalFileName

Type: string

Database type: text.

Stores the filename supplied for the uploaded file.

Used by the current download endpoint.



Filename handling must be treated carefully because filenames can be attacker-controlled input.



FileSizeBytes

Type: long

Database type: bigint.

Stores the actual file size in bytes.

Used in storage quota calculations.

ContentType

Type: string

Database type: text.

Stores the file's content type metadata.



Content type must not automatically be treated as proof of the file's actual content.



StorageObjectKey

Type: string

Database type: text.

Identifies where the physical file is stored.



Current local-storage implementation uses the upload file identifier as the storage key.



Future object-storage architecture is expected to use this field to identify an object in private object storage.



UploadedAt

Type: DateTime

Database type: timestamptz.

Records the upload completion time.

Uses UTC.

6.4 Relationship

Transfer 1 ──────── \* TransferFile



The relationship currently uses cascade delete.



Therefore:



Delete Transfer

&#x20;     ↓

Delete associated TransferFile records



Physical file cleanup is handled separately by backend cleanup logic.

7\. RecipientVerificationChallenge Entity

7.1 Business Meaning



RecipientVerificationChallenge represents an email verification challenge associated with a transfer recipient.



It provides the database foundation for recipient OTP/email verification.



The entity exists, but the complete recipient verification workflow is not yet implemented.



7.2 Current C# Model

public class RecipientVerificationChallenge

{

&#x20;   public Guid Id { get; set; } = Guid.NewGuid();



&#x20;   public Guid TransferId { get; set; }



&#x20;   public Transfer Transfer { get; set; } = null!;



&#x20;   public string RecipientEmail { get; set; } = string.Empty;



&#x20;   public string CodeHash { get; set; } = string.Empty;



&#x20;   public DateTime CodeExpiresAt { get; set; }



&#x20;   public int AttemptCount { get; set; } = 0;



&#x20;   public DateTime CreatedAt { get; set; } = DateTime.UtcNow;



&#x20;   public DateTime? ConsumedAt { get; set; }

}

7.3 Fields

Id

Type: Guid

Database type: uuid.

Primary key.

Uniquely identifies the challenge.

TransferId

Type: Guid

Database type: uuid.

Required foreign key to Transfer.

Transfer

Navigation property to the parent transfer.

RecipientEmail

Type: string

Database type: text.

Email address for which the verification challenge was issued.

CodeHash

Type: string

Database type: text.

Stores a hash of the verification code.

The actual OTP should not be stored in plaintext.

CodeExpiresAt

Type: DateTime

Database type: timestamptz.

Determines when the verification code becomes invalid.

AttemptCount

Type: int

Database type: integer.

Tracks verification attempts.



The field exists for future/enforced attempt limiting, but the complete enforcement workflow is currently incomplete.



CreatedAt

Type: DateTime

Database type: timestamptz.

Records when the challenge was created.

ConsumedAt

Type: DateTime?

Database type: timestamptz.

Nullable.

Intended to indicate that the verification challenge has been successfully consumed.

7.4 Relationship

Transfer 1 ──────── \* RecipientVerificationChallenge



Cascade delete is configured.



Deleting a transfer therefore removes its associated verification challenges from the database.

9\. Database Indexes Relevant to Entities



Current important indexes include:



Users

Unique Users.Email

Unique Users.Username



Purpose:



Prevent duplicate email addresses.

Prevent duplicate usernames.

Transfers

Unique Transfers.SecureToken

Transfers.UserId



Purpose:



Ensure secure tokens are unique.

Efficiently find transfers owned by a user.

TransferFiles

TransferFiles.TransferId



Purpose:



Efficiently retrieve files belonging to a transfer.

RecipientVerificationChallenges

RecipientVerificationChallenges.TransferId + RecipientEmail



This index is currently not unique.



Therefore multiple challenges can exist for the same transfer and recipient email.



10\. Entity-Level Security Considerations

User



Sensitive fields include:



PasswordHash

Email

authentication-related identity information



Rules:



Never expose PasswordHash through public APIs.

Never store plaintext passwords.

Never place passwords or password hashes in logs.

User ownership must be determined from authenticated identity, not an arbitrary client-supplied user ID.

Transfer



Sensitive fields include:



SecureToken

PasswordHash

ownership information



Rules:



Treat SecureToken as a secret access capability.

Do not expose internal ownership information unnecessarily.

Validate ownership for authenticated owner operations.

Validate expiration before recipient access.

Do not assume that possession of a token automatically satisfies recipient verification requirements when verification is enabled.

TransferFile



Important security concerns:



OriginalFileName is user-controlled input.

StorageObjectKey maps database metadata to physical/object storage.

File paths must remain inside the configured storage boundary.

Download authorization must be checked before opening the physical file.



The database record alone must not be treated as proof that an arbitrary filesystem path is safe.



RecipientVerificationChallenge



Sensitive fields include:



RecipientEmail

CodeHash



Rules:



Never store the raw OTP.

Do not expose CodeHash through an API response.

Expired challenges must not be accepted.

Attempt limits must eventually be enforced.

Consumed challenges must not be reusable.

Verification must eventually produce a controlled recipient authorization state/session.

12\. Entity Existence ≠ Feature Completion



This is an important rule for VASTRIX.



A database property or entity existing does not mean the associated feature is implemented.



Examples:



Transfer password



Transfer.PasswordHash exists.



Current conclusion:



Database field exists

&#x20;       ≠

Transfer password feature is complete



The password workflow, validation, authorization, and frontend behavior are still missing.



Recipient verification



RequireRecipientVerification exists.



RecipientVerificationChallenge also exists.



Current conclusion:



Database foundation exists

&#x20;       ≠

Recipient OTP verification is fully implemented



The complete generation, validation, attempt enforcement, recipient authorization, and download enforcement flow is still incomplete.



Storage object key



StorageObjectKey exists.



Current conclusion:



Storage metadata field exists

&#x20;       ≠

Object storage is implemented



Current physical storage remains the local filesystem.



AI tools must not mark these features as complete merely because the corresponding entity fields exist.



13\. Entity Lifecycle Concepts

User lifecycle

Registration

&#x20;    ↓

Active User

&#x20;    ↓

Disabled User



There is currently no separate deleted-user lifecycle documented in the implemented entity model.



Transfer lifecycle



The intended product lifecycle is:



PENDING

&#x20;  ↓

UPLOADING

&#x20;  ↓

UPLOADED

&#x20;  ↓

SCANNING

&#x20;  ↓

AVAILABLE

&#x20;  ↓

QUARANTINED / FAILED

&#x20;  ↓

EXPIRED

&#x20;  ↓

DELETED



However, TransferStatus does not currently exist in the entity model.



Current implementation primarily uses:



IsDeleted

ExpiresAt

Files



Therefore the lifecycle diagram above is a planned product lifecycle, not the current database state.



TransferFile lifecycle



Conceptually:



TUS upload

&#x20;   ↓

Physical file created

&#x20;   ↓

Upload completed

&#x20;   ↓

TransferFile metadata persisted

&#x20;   ↓

Available through transfer

&#x20;   ↓

Deleted during transfer cleanup



The exact atomic relationship between physical-file deletion and database deletion requires continued security/reliability work.



RecipientVerificationChallenge lifecycle



Intended:



Created

&#x20;  ↓

&#x20;  ├── Valid code → Consumed

&#x20;  ├── Expired → Invalid

&#x20;  └── Too many attempts → Invalid



The entity contains the fields required to support these states, but complete enforcement is not currently implemented.



14\. AI Rules for Entity Changes



Any AI assistant working on VASTRIX must follow these rules before modifying entities.



Rule 1 — Inspect actual source first



Before changing an entity:



Inspect the current C# class.

Inspect ApplicationDbContext.

Inspect existing migrations.

Check whether the property already exists.

Check how the property is used by controllers/services/workers.



Do not rely only on this memory document.



Rule 2 — Do not create duplicate concepts



Before adding a new field, determine whether an existing field already represents the concept.



Example:



Do not create another ownership field if Transfer.UserId already represents ownership.



Rule 3 — Entity changes require migration consideration



Adding, removing, or changing persistent properties can require:



Entity change

&#x20;     ↓

EF model change

&#x20;     ↓

Migration

&#x20;     ↓

Database update



Never assume that changing a C# entity automatically updates PostgreSQL.



Rule 4 — Do not modify the database directly as a substitute for migrations



For structural changes, use Entity Framework migrations unless there is a documented operational reason to use another mechanism.



SQL queries may be used for:



investigation

diagnostics

data verification

controlled data correction



but structural schema changes should remain synchronized with EF Core migrations.



Rule 5 — Preserve security boundaries



Do not change entity relationships or ownership semantics in a way that weakens:



user isolation

transfer ownership

token security

expiration enforcement

filesystem/object-storage boundaries

authentication/authorization

Rule 6 — Do not store large files in PostgreSQL



TransferFile stores metadata.



The actual large file belongs in the configured storage layer.



Current:



C:\\VASTRIX\_FileStore



Future:



Private Object Storage

Rule 7 — Do not expose sensitive entity fields



Never return these fields through public DTOs unless there is a very specific security-approved reason:



PasswordHash

CodeHash

internal ownership identifiers

internal storage paths

Rule 8 — Update project memory after significant entity changes



If an entity changes significantly, update:



PROJECT\_MEMORY/03\_DATABASE/ENTITIES.md



and, when applicable:



PROJECT\_MEMORY/03\_DATABASE/DATABASE\_SCHEMA.md

PROJECT\_MEMORY/03\_DATABASE/MIGRATIONS.md

PROJECT\_MEMORY/07\_BACKEND/BACKEND\_STATUS.md

Do not create a competing documentation source.
