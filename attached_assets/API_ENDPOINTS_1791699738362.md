\# 1. Purpose



This document is the current-state inventory of the VASTRIX backend API.



It describes:



\* Available endpoints.

\* HTTP methods and routes.

\* Authentication requirements.

\* Main request/response purpose.

\* Ownership/security behavior.

\* Current implementation gaps.

\* Important frontend/backend integration differences.



This document describes the \*\*implemented API\*\*, not the complete future product API.



The actual C# controllers, DTOs, middleware, and endpoint configuration remain the authoritative sources.

\# 6. Authentication Endpoints



\## 6.1 Register



```text

POST /api/Auth/register

```



Authentication:



```text

Anonymous

```



Purpose:



Creates a new VASTRIX user account.



The registration implementation handles:



\* Username/email input.

\* Normalization.

\* Duplicate checks.

\* Password hashing.

\* User creation.



Password hashing uses BCrypt.



\---



\## 6.2 Login



```text

POST /api/Auth/login

```



Authentication:



```text

Anonymous

```



Purpose:



Authenticates a user and issues a JWT.



The authentication flow validates:



1\. Username or email.

2\. Password.

3\. User existence.

4\. Disabled-user state.



The resulting JWT contains identity and authorization claims.



\---



\## 6.3 Swagger Login



```text

POST /api/Auth/swagger-login

```



Authentication:



```text

Anonymous

```



Purpose:



Provides authentication for the Swagger UI administrative/API testing workflow.



The successful authentication flow creates a protected Swagger authentication cookie.



Cookie:



```text

Swagger\_Auth\_Token

```



The cookie is configured as HttpOnly and uses strict SameSite behavior.



\---



\## 6.4 Swagger Logout



```text

POST /api/Auth/swagger-logout

```



Authentication:



```text

Anonymous

```



Purpose:



Removes the Swagger authentication cookie/session state.

\# 7. Transfer Endpoints



\## 7.1 List Current User's Transfers



```text

GET /api/Transfer

```



Authentication:



```text

Authenticated User

```



Purpose:



Returns transfers belonging to the authenticated user.



Security behavior:



\* Requires authentication.

\* Uses the authenticated user's identity.

\* Does not allow the client to select another user's ownership context.

\* Excludes soft-deleted transfers.



Conceptually:



```text

JWT

&#x20;↓

User ID

&#x20;↓

Transfers.UserId

&#x20;↓

Only that user's transfers

```



This is an important user-isolation boundary.



\---



\# 8. Create Transfer



```text

POST /api/Transfer/create

```



Authentication:



```text

Authenticated User

```



Purpose:



Creates a new transfer before file upload.



Current supported request concepts include:



```text

CustomMessage

RequireRecipientVerification

ExpiryDays

```



The authenticated user becomes the transfer owner.



The client does not supply an arbitrary owner ID to determine ownership.



\---



\## 8.1 Current Expiration Behavior



The API currently applies:



```text

ExpiryDays <= 0

&#x20;   → 7 days



ExpiryDays > 0

&#x20;   → limited to maximum 30 days

```



Therefore the current backend accepts arbitrary values between 1 and 30 rather than strictly enforcing:



```text

1

3

7

14

30

```



The frontend currently presents the five intended options.



This is a contract inconsistency.



\---



\## 8.2 Current Transfer Creation Limitations



The endpoint currently does not fully support all planned transfer controls.



Not currently represented by transfer creation:



```text

RecipientEmail

Transfer password

MaxDownloads

TransferStatus

DownloadCount

```



Recipient verification is only partially represented through the request flag and database foundation.

\# 9. Transfer Details



```text

GET /api/Transfer/details/{token}

```



Authentication:



```text

Anonymous

```



Purpose:



Allows a recipient to retrieve transfer information using the secure transfer token.



The endpoint currently:



\* Finds the transfer using `SecureToken`.

\* Rejects deleted transfers.

\* Checks expiration.

\* Returns transfer message.

\* Returns verification flag.

\* Returns expiration information.

\* Returns file metadata.



The token therefore acts as a bearer-style access capability.



\---



\## 9.1 Important Security Limitation



The endpoint currently does \*\*not\*\* enforce recipient verification even when:



```text

RequireRecipientVerification = true

```



Therefore:



```text

Verification requested

&#x20;       ≠

Verification enforced

```



The recipient can currently reach the transfer details endpoint using the token without completing an OTP verification process.



This is a known implementation gap.

\# 10. Download File



```text

GET /api/Transfer/download/{token}/{fileName}

```



Authentication:



```text

Anonymous

```



Purpose:



Downloads a file belonging to a valid transfer.



Current flow:



```text

Token

&#x20;↓

Find transfer

&#x20;↓

Check deleted state

&#x20;↓

Check expiration

&#x20;↓

Decode filename

&#x20;↓

Find file belonging to transfer

&#x20;↓

Resolve physical storage path

&#x20;↓

Validate path containment

&#x20;↓

Check file exists

&#x20;↓

Stream file

```



\---



\## 10.1 Current Storage



The current implementation uses:



```text

C:\\VASTRIX\_FileStore

```



The database contains file metadata while the physical file remains on the filesystem.



\---



\## 10.2 Path Security



The download implementation performs path containment validation against the storage root.



This is intended to prevent a filename or storage-path manipulation attack from escaping the allowed storage directory.



The server must remain authoritative for storage paths.



\---



\## 10.3 Current Download Limitations



The endpoint currently does not enforce:



```text

Recipient OTP verification

Transfer password

Maximum download count

Download count tracking

TransferStatus

Short-lived signed download URL

Object-storage authorization

```



The current URL also identifies the file using:



```text

{token}/{fileName}

```



rather than a dedicated file ID.



Duplicate filenames can therefore create ambiguity.



A future design should consider using the `TransferFile.Id` as the primary file identifier in download URLs.

\# 13. TUS Upload Completion



After a TUS upload completes, the backend performs additional validation.



The completion flow includes:



\* Authentication verification.

\* Metadata extraction.

\* Transfer lookup.

\* Transfer ownership verification.

\* Transfer expiration verification.

\* Physical file existence check.

\* Actual file length validation.

\* Database transaction.

\* User row locking.

\* User status verification.

\* Storage quota recalculation.

\* Final quota check.

\* `TransferFile` creation.

\* Transaction commit.



The database record contains:



```text

OriginalFileName

FileSizeBytes

ContentType

StorageObjectKey

UploadedAt

TransferId

```

\# 19. API vs Frontend Integration Issues



Current frontend implementation has several known mismatches.



\## API port mismatch



Backend:



```text

http://localhost:8080

```



Frontend transfer creation currently contains:



```text

http://localhost:5000/api/Transfer/create

```



The TUS endpoint uses the configured API base and currently targets the backend API base rather than this hardcoded transfer-creation URL.



\---



\## Authentication mismatch



The backend requires authentication for:



```text

POST /api/Transfer/create

/api/upload-stream

```



The current frontend upload flow does not attach the required JWT Authorization header.



Therefore the current frontend transfer/upload flow is not fully integrated with the current backend security requirements.



This must be solved by proper authentication integration.



The backend should \*\*not\*\* be weakened to accept unauthenticated uploads merely to make the current frontend work.



\---



\## Expiration mismatch



Frontend options:



```text

1

3

7

14

30

```



Backend currently accepts arbitrary positive values up to 30 days.



The frontend and backend contract should eventually be made consistent.



\---



\## Recipient verification mismatch



Frontend has a verification option.



Backend has:



```text

RequireRecipientVerification

RecipientVerificationChallenge

```



but complete enforcement is not implemented.



Therefore UI presence does not mean feature completion.

\# 20. API Access Principles



VASTRIX follows these security principles.



\## User identity



Protected endpoints should derive the current user from the authenticated identity.



Do not trust:



```text

client-supplied UserId

```



for ownership authorization.



\---



\## Transfer ownership



A transfer belongs to its authenticated owner.



TUS authorization verifies that the transfer belongs to the authenticated user.



\---



\## Recipient access



Recipient access currently uses:



```text

SecureToken

```



The token must be treated as a secret capability.



Future recipient controls should add verification/password/session checks without weakening the underlying token security.



\---



\## Expiration



Transfer access must be denied after:



```text

ExpiresAt

```



Current details and download endpoints perform expiration checks.



\---



\## Deleted transfers



A transfer marked:



```text

IsDeleted = true

```



must not remain accessible through normal transfer APIs.



\---



\# 21. API DTO Principle



API request/response DTOs should remain separate from database entities where appropriate.



Do not expose entity internals directly merely because a property exists in the database.



Particularly sensitive/internal properties include:



```text

PasswordHash

CodeHash

internal ownership information

physical storage paths

```

\# 22. API Error Handling



The application includes global exception handling middleware.



The purpose is to prevent uncontrolled exceptions from becoming raw API responses and to provide consistent error handling.



Request IDs are also used through request-ID middleware.



Security-sensitive information should not be exposed through error responses or logs.

\# 25. Security Change Rule



Never solve a frontend integration problem by weakening backend security.



For example:



```text

Frontend lacks JWT

&#x20;      ↓

WRONG:

Remove authentication from upload API

```



Correct approach:



```text

Frontend lacks JWT

&#x20;      ↓

Integrate proper authentication

&#x20;      ↓

Send authenticated request

&#x20;      ↓

Keep backend authorization

```

\# 26. API Completion Rule



The following distinction must always be maintained:



```text

Endpoint exists

&#x20;     ≠

Feature is complete

```



For example:



```text

POST /api/Transfer/create

```



exists and works as a transfer creation endpoint.



That does not mean the entire planned transfer feature is complete.



Likewise:



```text

/api/upload-stream

```



exists and supports TUS uploads.



That does not mean object storage, malware scanning, signed URLs, and all planned upload security features are complete.
