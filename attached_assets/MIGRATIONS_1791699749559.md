The initial migration created the transfer table used to represent secure file-transfer packages.


\# 6. Migration 2 — UpdateUserSchemaConstraints



\## Migration



```text

20260831013412\_UpdateUserSchemaConstraints

```



\## Purpose



This migration corrected and strengthened the user schema.



\## Main changes



\### Rename



The user name field was changed from:



```text

```



to:



```text

```



This aligns the database model with the current `User.Username` property.



\---



\## Unique email constraint



A unique constraint/index was added for:



```text

Users.Email

```



This prevents duplicate email addresses.



\---



\## Unique username constraint



A unique constraint/index was added for:



```text

Users.Username

```



This prevents duplicate usernames.



\---



\## Current result



The current user entity therefore uses:



```text

Username → unique

Email    → unique

```


```text

```



Current enum:



```csharp id="q8n7y2"

public enum UserRole

{

&#x20;   User = 0,

&#x20;   Admin = 1

}

```



\---



\## Security significance



The role is used by the backend authorization system.



Current administrative functionality includes the admin health endpoint.



Role information must not be treated as client-controlled data.



The backend derives authorization from the authenticated user's identity/claims and server-side authorization rules.

\# 8. Migration 4 — AddUserDisabledStatus



\## Migration



```text

20260909174806\_AddUserDisabledStatus

```



\## Purpose



Added the ability to disable user accounts.



\## Main change



Added:



```text

Users.IsDisabled

```



Database type:



```text

boolean

```



Default:



```text

false

```



\---



\## Security significance



Authentication does more than validate the JWT.



The backend also retrieves the user and checks whether the account is disabled.



Conceptually:



```text

JWT

&#x20;↓

User identity

&#x20;↓

Database user lookup

&#x20;↓

IsDisabled check

&#x20;↓

Allow / reject protected operation

```



Therefore, disabling a user can invalidate continued access even when a previously issued JWT has not yet expired.

\# 9. Migration 5 — AddRecipientVerificationChallenge



\## Migration



```text

20260914032002\_AddRecipientVerificationChallenge

```



\## Purpose



Introduced the database foundation for recipient email verification.



\## Table created



```text

RecipientVerificationChallenges

```



\---



\## Fields introduced



The table stores information corresponding to:



```text

Id

TransferId

RecipientEmail

CodeHash

CodeExpiresAt

AttemptCount

CreatedAt

ConsumedAt

```



\---



\## Security design



The database stores:



```text

CodeHash

```



rather than the raw verification code.



Conceptually:



```text

Generated OTP

&#x20;    ↓

Hash

&#x20;    ↓

Database

```



The plaintext OTP should only exist where necessary during the verification process and must not be persisted as plaintext.



\---



\## Relationship



```text

Transfer 1 ──────── \* RecipientVerificationChallenge

```



The relationship uses cascade deletion.



Therefore deleting the parent transfer also removes its associated verification challenge records.

\# 16. Important Difference: Model Change vs Data Change



These are different operations.



\## Schema/model change



Examples:



\* Add a column.

\* Remove a column.

\* Rename a property/column.

\* Add an index.

\* Change a relationship.

\* Change a column type.



These normally require an EF Core migration.



Concept:



```text

C# entity/model

&#x20;     ↓

EF migration

&#x20;     ↓

PostgreSQL schema

```



\---



\## Data change



Examples:



\* Correct a user's quota.

\* Disable a user.

\* Correct a stored email.

\* Remove obsolete data.



These modify existing records rather than changing the database structure.



They must be handled carefully and must not be confused with creating a migration.

\# 17. PowerShell vs SQL Reminder



VASTRIX development frequently uses PowerShell.



SQL statements are \*\*not PowerShell commands\*\*.



For example, this is SQL:



```sql

SELECT \*

FROM "Users";

```



It should not simply be pasted into a PowerShell prompt.



Similarly:



```sql

UPDATE "Users"

SET "StorageQuotaBytes" = 5368709120;

```



is SQL, not PowerShell syntax.



When investigating or changing database data, clearly identify whether the command is:



```text

PowerShell

SQL

C#

EF Core CLI

```



This distinction is especially important for future AI-assisted troubleshooting.

\# 18. Migration Safety Rules



\## Rule 1 — Never assume a migration is unnecessary



If an entity changes, check:



```text

dotnet ef migrations has-pending-model-changes

```



Do not rely on memory.



\---



\## Rule 2 — Never delete historical migrations casually



Existing migrations represent database history.



Deleting or rewriting an already-applied migration can cause schema/version inconsistencies.



Only alter migration history deliberately and with a clear database migration strategy.



\---



\## Rule 3 — Review generated migrations



A generated migration can contain unintended changes.



Before applying it, inspect:



\* Tables affected.

\* Columns added/removed.

\* Rename operations.

\* Indexes.

\* Foreign keys.

\* Defaults.

\* Nullability.

\* Data-loss warnings.



\---



\## Rule 4 — Renames require special care



Changing:



```text

Name

```



to:



```text

Username

```



is different from simply deleting one column and adding another.



Where appropriate, migrations should preserve existing data through explicit rename operations.



\---



\## Rule 5 — Do not use direct database changes to hide EF model differences



If the entity model changes but no migration exists, the system can become inconsistent.



The correct goal is:



```text

C# Model

&#x20;  =

EF Migration Model

&#x20;  =

Database Schema

```



for the intended deployed version.

\# 19. Current Migration-Related Risks



The current migration history is valid and synchronized, but future development can introduce risks.



Important risks include:



\### Schema drift



Database manually changed without corresponding EF model/migration changes.



\### Migration drift



EF model changed without creating a migration.



\### Environment mismatch



Development database and another environment may have different migration states.



\### Destructive changes



Removing or changing columns can cause data loss.



\### Incorrect migration project



Using the wrong `--project` or `--startup-project` path can cause EF CLI errors.



The correct Infrastructure path must always be used.

\# 20. Migration History and Feature Status



Migration presence must not be interpreted as complete feature implementation.



For example:



```text

```



means:



```text

Recipient verification database foundation exists

```



It does \*\*not\*\* mean:



```text

Complete recipient verification feature exists

```



The complete feature still requires application-level logic such as:



\* Challenge generation.

\* OTP delivery.

\* OTP validation.

\* Expiration enforcement.

\* Attempt enforcement.

\* Consumed-state enforcement.

\* Recipient authorization/session handling.

\* Download enforcement.

\* Frontend recipient verification UI.
